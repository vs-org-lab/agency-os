# Sub-projeto 3A — Dinheiro — Plano de implementação

> **Para agentes:** SUB-SKILL OBRIGATÓRIA: usar `superpowers:subagent-driven-development` ou `superpowers:executing-plans` para executar este plano tarefa a tarefa. Os passos usam caixas (`- [ ]`) para acompanhamento.

**Objetivo:** o ecrã S-09 com o ano em entrou, em aberto e saiu, despesas e subscrições com recibo, leitura de recibos como proposta e despesas faturáveis ligadas a pedidos de pagamento, visíveis no portal.

**Arquitetura:** um módulo novo `apps/web/src/modules/money`.

- Lê os pagamentos e os pedidos do 1D, só para leitura, e é dono das tabelas `expenses` e `subscriptions`.
- **Recibos:**
  - são carregados antes de a despesa existir, em `money/<organização>/receipts/<id>`, com um link assinado;
  - o servidor confirma o tipo real e o tamanho, e propõe os campos com um leitor de visão;
  - a despesa guarda o caminho ao ser gravada.
- O portal lê os comprovativos por uma vista com `security_barrier`.

**Stack:** a existente. A leitura de recibos usa a API compatível com OpenAI da Groq, com `fetch`. Sem dependências novas.

**Spec:** [docs/superpowers/specs/2026-10-14-money-design.md](../specs/2026-10-14-money-design.md)

## Restrições globais

- As dos planos anteriores: TDD; inglês no código e PT-PT na documentação; migrações com dry-run; sem custo; sem linhas de atribuição a IA; escapes, barras invertidas e regex só com a ferramenta Edit ou com scripts em ficheiro (nunca backticks em `node -e`); fronteira de módulos; segredos nunca mostrados.
- **Valores do spec:**
  - **categorias:** `software`, `advertising`, `freelancers`, `equipment`, `travel`, `training` e `other`;
  - **ciclos:** `monthly` e `annual`; **estados de subscrição:** `active` e `cancelled`;
  - **recibo:** JPEG, PNG, WebP ou PDF, até 10 MB (10_485_760 bytes);
  - **links:** de 15 minutos;
  - **renovações em destaque:** nos próximos 7 dias e atrasadas;
  - **moedas:** EUR, GBP, USD e AOA, com totais por moeda;
  - **ano:** o de Lisboa;
  - **leitor:** `RECEIPT_READER=groq|fake`, modelo `meta-llama/llama-4-scout-17b-16e-instruct`, chave `GROQ_API_KEY`.
- **Acesso:**
  - ler com `canReadBilling` / `app.can_read_billing`, escrever com `canWriteBilling` / `app.can_write_billing`;
  - no portal, o decisor e o financeiro do cliente.
- **Recusas:** `not_found`, `invalid_input`, `invalid_file` e `invalid_state`.

## Foco de revisão

1. **Caminho de recibo de outra organização** (`money/<outra-org>/receipts/<id>`) ao gravar uma despesa: recusado com `invalid_file`. Teste na Task 4 (`receipts outside the organisation are refused`).
2. **Proposta do leitor com valores estranhos** (valor negativo, texto no valor, moeda `XYZ`, data impossível, JSON partido): campo vazio, sem erro. Teste na Task 3 (`odd answers become empty fields`).
3. **Ligar a um pedido de outro cliente ou anulado:** recusado com `invalid_input`. Teste na Task 4 (`expenses link only to their client's live requests`).
4. **Renovação a 31 de janeiro mensal e a 29 de fevereiro anual:** passa ao último dia do mês seguinte e a 28 de fevereiro. Teste na Task 2 (`cycles keep to the last day of short months`).
5. **Comprovativo de um cliente pedido por outro cliente ou pelo operacional:** não aparece. Teste na Task 7 (`receipts are shown only to the client's decision maker and finance`).

### Task 3: Leitor de recibos

**Ficheiros:**

- `platform/receipt-reader.ts` (+ teste);
- `platform/env.ts`: `parseReceiptReaderEnv`.

**Interfaces:**

- `type ReceiptProposal = { spentOn: string | null; vendor: string | null; amount: string | null; currency: Currency | null; description: string | null }`.
- `type ReceiptReader = { read(image: Uint8Array, mimeType: 'image/jpeg' | 'image/png' | 'image/webp'): Promise<ReceiptProposal> }`.
- `createGroqReceiptReader(apiKey, fetcher = fetch)`:
  - faz `POST https://api.groq.com/openai/v1/chat/completions` com o modelo do spec, `response_format: { type: 'json_object' }`, `temperature: 0` e a imagem em `data:` base64;
  - o prompt pede JSON `{ date, vendor, total, currency, description }`;
  - um erro HTTP ou de rede dá uma proposta vazia.
- `parseProposal(raw: unknown) → ReceiptProposal`:
  - data válida `YYYY-MM-DD`;
  - valor > 0 com até 2 casas, aceitando `12,50` e `1.234,56`;
  - moeda num dos quatro valores;
  - textos cortados a 120 e 500 caracteres;
  - tudo o resto fica `null`.
- `FAKE_PROPOSAL` e `receiptReader(): ReceiptReader | null`: `fake`, `groq` com a chave, ou `null`.

**Passos:**

- [ ] Testes:
  - `the groq request carries the model, the image and json mode`;
  - `odd answers become empty fields` (foco 2);
  - `portuguese amounts are read`;
  - `http errors give an empty proposal`;
  - `the reader follows the configuration`.
- [ ] FALHA → implementar → PASSA.
- [ ] Ensaio real único com a chave do `.env.local` e um recibo PNG gerado (texto desenhado): confirma o modelo e o formato. O resultado vai para o registo, sem mostrar a chave. Se o modelo não existir, decidir pelo modelo de visão disponível na Groq e registar a decisão.
- [ ] Commit.

### Task 4: Despesas, recibos e subscrições

**Ficheiros:**

- `modules/money/{access.ts,expenses.ts,receipts.ts,subscriptions.ts,testing.ts,server.ts,index.ts}`, com os testes `expenses.db.test.ts` e `subscriptions.db.test.ts`;
- `LibraryStorage` reutilizado;
- ações de auditoria novas:
  - `money.expense_created`, `money.expense_updated` e `money.expense_deleted`;
  - `money.expense_linked` e `money.expense_unlinked`;
  - `money.subscription_created`, `money.subscription_updated`, `money.subscription_cancelled` e `money.subscription_renewed`.

**Interfaces:**

- `MoneyDeps = { contexts; storage: LibraryStorage; reader?: ReceiptReader; now? }`.
- `startReceiptUpload(claims, { fileName, sizeBytes }) → { ok: true; receiptId; uploadUrl } | NotFound | invalid_input`:
  - só para quem escreve;
  - tamanho ≤ 10 MB;
  - caminho `money/<org>/receipts/<receiptId>`.
- `readReceipt(claims, receiptId) → { ok: true; mimeType; proposal: ReceiptProposal | null } | NotFound | invalid_file`:
  - descarrega o objeto e confirma o tipo real (JPEG, PNG, WebP ou PDF) e o tamanho;
  - um objeto inválido é apagado;
  - lê a proposta só nas imagens e quando há leitor.
- `saveExpense(claims, input: { id?; spentOn; vendor; description; category; amount; currency; clientId?; receiptId?; receiptName?; subscriptionId? }) → { ok: true; id } | NotFound | invalid_input | invalid_file`:
  - valida tudo;
  - o recibo tem de existir no caminho da organização e ser de tipo válido;
  - o cliente tem de ser da organização;
  - não se muda o cliente de uma despesa ligada.
- `deleteExpense(claims, id) → OK | NotFound | invalid_state`: recusa se estiver ligada; apaga o recibo.
- `linkExpense(claims, { expenseId, paymentRequestId | null }) → OK | NotFound | invalid_input`: o pedido tem de ser do cliente da despesa e não estar anulado.
- `saveSubscription`, `cancelSubscription(claims, id)` e `renewSubscription(claims, { id, receiptId?, receiptName? }) → { ok: true; expenseId }`:
  - a renovação cria a despesa com a data da renovação, o valor, a moeda e a categoria da subscrição;
  - depois avança `nextRenewalOn` com `nextRenewal`;
  - uma subscrição cancelada não renova.

**Passos:**

- [ ] Testes:
  - `writers upload receipts and the type is checked` (PNG aceite com proposta `fake`; texto renomeado `.png` recusado e apagado; PDF aceite sem proposta);
  - `receipts outside the organisation are refused` (foco 1);
  - `expenses are validated and audited`;
  - `managers read but cannot write`;
  - `expenses link only to their client's live requests` (foco 3);
  - `a linked expense cannot be deleted or change client`;
  - `renewing creates the expense and moves the date`;
  - `cancelled subscriptions do not renew`.
- [ ] FALHA → implementar → PASSA → commit.
